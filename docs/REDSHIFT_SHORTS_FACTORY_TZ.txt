0. КАК ЧИТАТЬ ЭТОТ ДОКУМЕНТ (ИНСТРУКЦИЯ ДЛЯ АГЕНТА CURSOR)
================================================================================

Ты — инженер-исполнитель. Этот документ — единственный источник правды.
Правила работы:

0.1. Не переписывай существующий рабочий pipeline «с нуля». Раздел 24 описывает
     миграцию: что оставить, что обернуть адаптером, что выбросить.
0.2. Каждая стадия pipeline — отдельный модуль с чистым контрактом:
     вход = JSON-файл предыдущей стадии, выход = JSON-файл своей стадии.
     Никаких скрытых глобальных состояний. Любую стадию можно запустить одну.
0.3. Все числовые константы вынеси в config/*.yaml. В коде — только имена.
     Числа в разделах 1, 2, 8, 26 — это дефолты конфига, а не магические числа.
0.4. Любой вызов внешнего API идёт ТОЛЬКО через core/clients/* с обязательными:
     кэш по хэшу запроса → бюджет-гард → ретрай с backoff → лог стоимости.
     Прямой requests.post к API в бизнес-логике = ошибка ревью.
0.5. Если данных для решения не хватает — не выдумывай. Пиши в
     runs/<run_id>/questions.md и продолжай по деградационной лестнице (раздел 4.6).
0.6. Definition of Done для каждой стадии — раздел 25. Стадия не считается
     сделанной, пока не проходит свой smoke-тест на моках (--dry-run).
0.7. Язык кода и комментариев — английский. Язык промптов к LLM — русский для
     сценария, английский для поисковых запросов и генерации изображений.
0.8. Никогда не логируй значения API-ключей. Все ключи — только из env/secrets.

1. РЕЗУЛЬТАТЫ РЕВЕРС-ИНЖИНИРИНГА РЕФЕРЕНСОВ (ИЗМЕРЕННЫЕ ДАННЫЕ)
================================================================================

Анализ выполнен инструментально: покадровое scene-detection (ffmpeg select=scene),
контактные листы кадров, замер тишины и громкости. Это не «на глаз», это цифры.

--------------------------------------------------------------------------------
1.1. РЕФЕРЕНС V1 — «SPLIT-SCREEN» (файл AQNS..., 77.4 c, 720x1280, 30 fps)
--------------------------------------------------------------------------------
Формат кадра:
  - Верхние ~50% — контент (скриншот X/Twitter-поста, запись экрана сервиса,
    кинематографичный футаж, сетка кадров раскадровки).
  - Нижние ~50% — говорящая голова, НИКОГДА не исчезает, постоянный кадр.
  - Субтитры — на стыке половин, 2 строки, мелкий белый шрифт, фразами
    (не по одному слову), ~3–5 слов на экран.
  - Ватермарка канала в верхнем левом углу поверх верхней половины.

Ритм монтажа (меняется ТОЛЬКО верхняя половина):
  Всего смен верхнего плана: 24 за 77.4 c
  Интервалы (c): 6.13, 5.27, 1.20, 12.80, 0.73, 0.80, 1.70, 0.30, 0.20, 0.20,
                 0.20, 0.20, 0.47, 1.57, 5.87, 3.60, 6.63, 0.70, 1.17, 3.63,
                 3.43, 9.43, 2.40
  Медиана: 1.57 c | Среднее: 2.98 c | Мин: 0.20 c | Макс: 12.80 c
  Распределение: ≤0.35 c — 5 шт (серия-вспышка), 0.35–1.5 — 6, 1.5–3 — 3, >3 — 9

ВЫВОД: это «объяснительный» ритм. Длинные удержания (5–12 c) допустимы только
когда на экране пошагово разбирается интерфейс/скриншот и голос его комментирует.
Внутри длинного удержания обязателен внутрикадровый мув (zoom/pan/подсветка).
Серия из 5 кадров по 0.20 c — это «карусель результатов» (быстрый показ пачки
примеров). Для REDSHIFT берём этот паттерн как «BURST».

--------------------------------------------------------------------------------
1.2. РЕФЕРЕНС V2 — «B-ROLL + MEME MONTAGE» (Китай vs Илон Маск, 81.0 c, 60 fps)
--------------------------------------------------------------------------------
ЭТО ГЛАВНЫЙ РЕФЕРЕНС ДИНАМИКИ. Говорящей головы нет вообще, только закадр.

Формат кадра:
  - Исходники горизонтальные → вписаны по ширине в центр, сверху и снизу
    размытая копия того же кадра (blurred duplicate fill). Никаких чёрных полос.
  - Субтитры — КАРАОКЕ ПО ОДНОМУ СЛОВУ. Подтверждено покадрово:
    «В» → «2000» → «2011-» → «Илона» → «Маска» → «спросили,» → «представляет»
    Смена слова каждые ~0.30–0.60 c. Шрифт жирный, белый, тяжёлая тёмная тень,
    по центру по горизонтали, по вертикали ≈57% высоты кадра (чуть ниже центра).
  - Ватермарка по центру-низу, полупрозрачная.

Ритм монтажа:
  Всего склеек: 51 за 81.0 c
  Медиана: 1.54 c | Среднее: 1.54 c | Мин: 0.03 c | МАКС: 2.85 c
  Распределение: ≤0.35 c — 5, 0.35–1.5 — 19, 1.5–3.0 — 26, >3.0 — НОЛЬ

КРИТИЧЕСКИЙ ВЫВОД (главное правило динамики для REDSHIFT):
  В таком формате НИ ОДИН план не живёт дольше 2.9 секунды. Никогда.
  Среднее и медиана совпадают (1.54) — ритм ровный, без провалов.
  Вставки 0.03–0.4 c — это флеш-кадры на входе мема и на пуантах.

Логика подбора картинки: каждый план иллюстрирует буквально то слово, которое
сейчас звучит. Прозвучало «BYD» — на экране лого/машина BYD. Прозвучало
«рассмеялся» — реакция Маска. Прозвучало «Пошлину» — Трамп у трибуны.
То есть материал подбирается на уровне СУЩНОСТИ В ПРЕДЛОЖЕНИИ, а не темы абзаца.

Логика мемов: мемы = реакционные вставки (Дэнни Де Вито, хлопающий Обама,
«шокированный» Маск, человек, хлебающий суп). Они стоят строго в тех точках,
где нарратив делает эмоциональный поворот: удивление, скепсис, злорадство,
разочарование. Мем ВСЕГДА совпадает с эмоцией фразы, а не с её темой.

Аудио: тишины длиннее 0.25 c при пороге −32 dB — НЕТ ВООБЩЕ. Средняя громкость
−17.1 dB, пик −2.8 dB. Значит: сплошная музыкальная подложка + плотный VO без
дыр, сильная компрессия. Пустоты в звуке в этом формате запрещены.

--------------------------------------------------------------------------------
1.3. РЕФЕРЕНС V3 — «TALKING HEAD HERO» (Топ-1 AI для SHORTS, 33.1 c, ~30 fps)
--------------------------------------------------------------------------------
ЭТО РЕФЕРЕНС ГОВОРЯЩЕЙ ГОЛОВЫ, который заказчик хочет как основу присутствия.

Формат кадра:
  - Ведущий занимает весь кадр (средний план, микрофон в кадре, фон — комната
    с боке). Он в кадре большую часть времени.
  - Верхняя треть — «полка» для оверлеев: окна браузера/интерфейсов со
    скруглёнными углами, лёгким наклоном (2–5°) и мягкой тенью, логотипы-карточки,
    которые влетают с 3D-вращением и пружинкой (bounce, overshoot ~12%).
  - Иногда ведущий полностью исчезает → фулскрин записи экрана / чёрный фон с
    3D-сеткой и красными частицами (переходная «пустая» сцена).
  - Иногда в кадр входит мокап телефона (нижний левый угол) поверх ведущего.
  - Субтитры — 1–3 слова, по центру, ниже середины, полупрозрачный белый;
    для ключевых цифр — крупный жирный акцент («100 shorts»).

Ритм:
  Всего изменений сцены: 35 за 33.1 c
  Медиана интервала: 0.20 c | Среднее: 0.85 c | Макс: 4.15 c
  ≤0.35 c — 21 событие, 0.35–1.5 — 6, 1.5–3 — 4, >3 — 3

ВАЖНАЯ ИНТЕРПРЕТАЦИЯ: медиана 0.20 c здесь — это НЕ склейки, а поп-ины оверлеев
(влёт логотипа, появление окна, вспышка сетки). Реальных смен сцены ~10 за 33 c,
то есть ~3.3 c на смысловой блок. Динамику держит не резка, а НЕПРЕРЫВНОЕ
ДВИЖЕНИЕ ОВЕРЛЕЕВ поверх статичного ведущего.
Отсюда правило: если ведущий в кадре — можно держать план до 4.2 c, НО в каждую
секунду обязано происходить хотя бы одно микрособытие (влёт, уход, подсветка,
скейл, подчёркивание слова).

Аудио: средняя −26.9 dB, пауза ≥0.25 c всего одна. Голос доминирует, музыка тише,
чем в V2. Для режима HERO музыку опускаем на 4–6 dB относительно режима B-ROLL.

2. ЦЕЛЕВОЙ ФОРМАТ REDSHIFT: ТРИ РЕЖИМА КАДРА И ПРАВИЛА ПЕРЕКЛЮЧЕНИЯ
================================================================================

2.1. РЕЖИМЫ (три, как и просил заказчик)
--------------------------------------------------------------------------------
MODE_A  «SPLIT»   — ведущий в нижней половине, контент сверху.
  Геометрия: футаж    y = 0 … 0.52H (safe-crop 9:8)
             ведущий  y = 0.48H … 1.0H (feather-маска на стыке 24 px)
             стык     тонкая crimson-линия 2 px с glow 40%, opacity 0.35
  Субтитры: 2 строки, 3–5 слов, кегль 46–54 px, y ≈ 0.455H (над стыком)
  Когда использовать: объяснение схемы, разбор скриншота статьи, сравнение,
                      «смотрите, что произошло».
  Потолок удержания верхнего плана: 6.0 c (в референсе было 12.8 — режем).

MODE_B  «FULL_BROLL» — ведущего нет, полный кадр футажа, закадровый голос.
  Геометрия: футаж на весь кадр. Горизонтальный исходник → blurred duplicate fill
             (blur σ=28, scale 1.25, brightness −18%) + основной кадр по центру.
  Субтитры: КАРАОКЕ ПОСЛОВНО, Space Grotesk Bold 78–88 px, y = 0.57H, центр,
            цвет #F1F5F9, crimson glow 0 0 22px rgba(225,29,72,.55),
            тень 0 6px 18px rgba(0,0,0,.85). Активное слово scale 1.06,
            подсветка ключевых сущностей — #F43F5E.
            БЕЛЫХ ТОЛСТЫХ ОБВОДОК НЕТ (запрет брендбука).
  Когда использовать: перечисления, нагнетание, кульминация, «вау»-визуал,
                      мемы, любые кадры, которые сами по себе сильные.
  Потолок удержания плана: 2.9 c. Медиана-цель: 1.5 c.

MODE_C  «HERO»    — ведущий на весь экран, оверлеи в верхней трети.
  Геометрия: ведущий фулл-фрейм. «Полка оверлеев» y = 0.06H … 0.38H.
             Окна/скрины: border-radius 18 px, наклон ±3°, тень
             0 24px 60px rgba(0,0,0,.6), тонкая рамка rgba(241,245,249,.12).
             Влёт: 0.28 c, ease-out-back (overshoot 12%), + whoosh.
  Субтитры: 1–3 слова, кегль 58–66 px, y = 0.78H, никогда не поверх глаз/рта.
  Когда использовать: личное обращение, вопрос зрителю, тезис, финал/CTA.
  Потолок удержания: 4.2 c, НО обязательное микрособытие каждую ≤1.0 c.

2.2. ПРАВИЛА ПЕРЕКЛЮЧЕНИЯ (state machine, реализовать в 03_shotlist)
--------------------------------------------------------------------------------
R1. Видео ВСЕГДА начинается с MODE_B или MODE_C — в первые 0.4 c обязан быть
    визуальный хук + крупный текст. Начинать со сплита запрещено (слабый хук).
R2. Ведущий (MODE_A или MODE_C) обязан занимать 40–70% хронометража — норма
    брендбука. Считается по сумме длительностей блоков A и C.
R3. Один режим подряд — не дольше 12 c. После 12 c обязана быть смена режима.
R4. Смена режима — не чаще 1 раза в 3.5 c (иначе каша).
R5. MODE_B обязателен минимум 2 раза за ролик и обязан покрывать самый сильный
    визуал ролика (JWST-снимок, симуляция, «вау»-кадр).
R6. Мем всегда играет в MODE_B (полный кадр) — исключение: PiP-мем 0.5 c в углу
    во время MODE_C, если мем короткий и реакционный.
R7. Финальные 2.0 c — всегда MODE_C (лицо) + анимация SUBSCRIBE снизу.
R8. Переход между режимами всегда сопровождается звуковым событием (whoosh/
    impact/ui-click) и одним из переходов брендбука:
    particle dissolve | soft warp | holographic flicker | morph.
    Жёсткая склейка без звука между режимами = ошибка QC.
R9. При морф-переходе внутри MODE_C лицо остаётся, меняется фон
    (космос → схема → ДНК → нейросеть) — сигнатурный приём бренда.

2.3. РИТМИЧЕСКАЯ СЕТКА (то, что даёт ощущение «динамично, как в референсе»)
--------------------------------------------------------------------------------
Базовая единица — BEAT (смысловой удар), 1 фраза сценария = 1–3 бита.

Профиль ритма по хронометражу ролика 45 c:
  0.0–2.0  c  HOOK      — 3–5 планов, по 0.4–0.7 c, максимальная плотность
  2.0–8.0  c  SETUP     — планы по 1.4–2.2 c, вводим контекст
  8.0–30.0 c  BODY      — базовый ритм 1.2–2.2 c + 1–2 BURST-серии
  30.0–40.0c  CLIMAX    — ускорение до 0.8–1.4 c, самый сильный визуал
  40.0–45.0c  CLOSER    — 1 длинный план 2.5–3.5 c (лицо) + SUBSCRIBE 2.0 c

BURST-серия (из V1/V2): 3–7 планов по 0.10–0.35 c подряд. Ставится ТОЛЬКО на:
  - перечисление (три примера, пять моделей, семь миссий),
  - нарастание перед пуантом,
  - «вот что произошло дальше» — быстрый монтаж последствий.
Норма: 1–2 BURST на ролик. Три и более — перегруз, QC отклоняет.

FLASH-кадр 1–2 фрейма (0.03–0.07 c): белый #F1F5F9 при 35% или crimson #E11D48
при 45%, только на: вход мема, вход крупной цифры, момент «взлома/аварии/удара».
Не более 6 флешей на ролик (эпилепсия-безопасность + вкус).

ЗАПРЕТ: любые ≥3 вспышки за 1 секунду (риск фотосенситивности и страйка).

2.4. СУБТИТРЫ — ТОЧНАЯ СПЕЦИФИКАЦИЯ
--------------------------------------------------------------------------------
Источник таймингов: пословный форс-алайнмент VO (WhisperX / faster-whisper
word_timestamps=True). НЕ на глаз, не по длине текста.

Общие правила:
  - Safe zone: top 14% (UI YouTube), bottom 18% (заголовок/CTA), right 12%.
  - Текст никогда не на ярком объекте: если средняя яркость подложки под
    боксом текста > 0.55, автоматически подкладывать градиент
    linear-gradient(transparent, rgba(5,5,8,.72)) высотой 1.6× бокса.
  - Chromatic aberration: копия текста #E11D48 со сдвигом (−1.5px, 0) и копия
    #22D3EE со сдвигом (+1.5px, 0), opacity 0.30, под основным слоем.
  - Ключевые сущности (имена моделей, названия миссий, цифры) — цветом #F43F5E
    и на 8% крупнее. Список сущностей приходит из script.json (поле entities).
  - Числа и единицы — JetBrains Mono.

2.5. ФИНАЛ РОЛИКА — ОБЯЗАТЕЛЬНАЯ КОНСТРУКЦИЯ
--------------------------------------------------------------------------------
Заказчик задал три типа концовки. Реализовать как enum closer_type:

  CLOSER_QUESTION   — прямой вопрос зрителю в кадре (MODE_C).
                      Пример: «Как думаете, ИИ действительно нас заменит?»
  CLOSER_PUNCH      — фраза-пуант + мем (мем в MODE_B, 0.6–0.9 c, затем возврат
                      на лицо). Пример: «А вы думали, нас ИИ не захватит?»
  CLOSER_LOOP       — последняя фраза семантически замыкается на первую, чтобы
                      ролик зациклился без шва (лучший для удержания).

Правила:
  - Тип выбирается сценаристом и пишется в script.json.
  - CLOSER_PUNCH разрешён не чаще чем в 1 ролике из 3 (иначе бренд сползает
    в юмористический канал, а позиционирование — «премиальный проводник»).
  - CLOSER_LOOP — приоритетный по умолчанию для космоса и научпопа.
  - В последние 2.0 c всегда: анимация красной кнопки SUBSCRIBE снизу вверх
    (ease-out, 0.45 c, с лёгким пружинным overshoot), знак REDSHIFT,
    звук subscribe_pop.wav (−12 dB под VO).
  - Текст CTA не перекрывает лицо, ставится в зоне y = 0.80–0.88H.

4.2. КЭШ (три уровня)
--------------------------------------------------------------------------------
  cache/objects/<sha256>[.ext]   — любые скачанные медиа. Вечный.
                                   Рядом <sha256>.meta.json: src_url, license,
                                   author, width, height, duration, phash,
                                   motion_score, sharpness, colors, first_seen.
  cache/queries/<sha1(query+source+params)>.json — выдача поисковика. TTL 14 д.
  cache/llm/<sha1(model+prompt+params)>.json     — ответ LLM. TTL 30 д.

Правила:
  - ПЕРЕД любым сетевым вызовом — обязательный lookup в кэше. Без исключений.
  - Кэш общий между run'ами (это ключ к экономии: 40–60% материала повторно
    используется между роликами одной тематики).
  - Дедуп по pHash: если новый ассет имеет hamming distance ≤6 к уже
    существующему — не скачиваем, переиспользуем существующий.
  - assets_used_history.json хранит, какие sha256 использованы в последних
    30 роликах. ASSET HUNTER штрафует повторы (см. 9.6), чтобы канал не

4.4. РЕТРАИ
--------------------------------------------------------------------------------
  - Сетевые/5xx/timeout: 3 попытки, экспоненциальный backoff 2s/6s/18s + джиттер.
  - 429: уважать Retry-After, максимум 5 попыток, затем — другой источник.
  - Circuit breaker на провайдера: 5 подряд ошибок → провайдер выключается
    на 10 минут, трафик уходит на следующий по лестнице источников (9.3).
  - Невалидный JSON от LLM: 1 повтор с добавкой «Return ONLY valid JSON. No
    prose, no markdown fences.» Затем — жёсткий парсер (вырезать между первой
    { и последней }). Затем — fail стадии.

4.5. ПАРАЛЛЕЛИЗМ
--------------------------------------------------------------------------------
  - s04 (поиск ассетов) — пул из 8 воркеров по битам.
  - s09 (VO+аватар) запускать ПАРАЛЛЕЛЬНО с s04–s06: голос не зависит от
    подбора материала. Это экономит 5–9 минут на ролик.
  - s08 (инфографика) — параллельно с s05.
  - Всё, что пишет в кэш, использует файловый лок на sha256.

4.6. ДЕГРАДАЦИОННАЯ ЛЕСТНИЦА (ролик обязан выйти всегда)
--------------------------------------------------------------------------------
LVL 0  Норма: всё по ТЗ.
LVL 1  Нет бюджета на Magnific-генерацию → только сток + архивы + процедурные
       брендовые фоны из assets/backplates.
LVL 2  Нет бюджета на Gemini → критик работает только на Grok, порог приёма
       поднимается на +0.5 (строже, потому что нет второго мнения).
LVL 3  Нет бюджета на vision вообще → работает только L0-фильтр (детерминированный)
       + правило «релевантность по совпадению сущностей в имени/тегах ассета».
       Ролик помечается needs_human_review=true.
LVL 4  HeyGen недоступен → весь ролик в MODE_B (закадровый голос), лицо не
       используется, финал — логотип вместо лица. Флаг needs_human_review.
LVL 5  Нет 30% материала → длительность ролика сокращается (выкидываем самые
       слабые биты сценария по score), но не короче 24 c.
LVL 6  Всё плохо → сохраняем run как draft, шлём в Telegram отчёт «что упало и
       чего не хватило», НЕ публикуем. Ничего не удаляем из кэша.

Каждый уровень пишется в state.degradation_level и в описание ролика для

5.2. АЛГОРИТМ
--------------------------------------------------------------------------------
1) Fetch: параллельно все фиды, окно — последние 72 часа. Кэш ETag/Last-Modified.
2) Normalize: {title, summary, url, source, published_at, image_url, pillar}.
3) Dedupe: SimHash по title+summary, порог 0.86; кластеризация «одна история —
   много источников». У кластера выбирается «первоисточник» (наивысший
   authority_score из sources.yaml) и 2–4 «подтверждения».
4) Hard filters (выбрасываем сразу):
   - старше 96 часов, если это не «вечная» научная тема;
   - политика, война, преступления, катастрофы с жертвами → skip (не наш бренд);
   - медицинские советы/лечение конкретных болезней → skip (YMYL-риск);
   - пресс-релизы без фактуры (нет цифр, нет источника, нет визуала);
   - тема уже использовалась за последние 60 дней (topics_history.json).
5) Scoring (0–100), веса в config:
   novelty            25   — насколько это новое/впервые (LLM-оценка + дата)
   visual_potential   25   — есть ли, ЧТО показать (снимок, симуляция, схема)
   wow_factor         20   — «тихий восторг»: масштаб, контринтуитивность
   pillar_fit         15   — совпадение со столпами REDSHIFT
   buzz               10   — свежий интерес (Grok live X), но НЕ хайп ради хайпа
   authority           5   — качество источника
   ШТРАФЫ: −20 если тема требует объяснения дольше 60 c;
           −15 если нет ни одного бесплатного визуала;
           −25 если сходство с последними 30 темами > 0.7 (эмбеддинги).
6) Visual pre-check (ВАЖНО, дешёвый шаг): для топ-8 кандидатов сразу дёрнуть
   NASA/Pexels/Pixabay поиск по 2 ключевым сущностям и посчитать, сколько
   релевантных ассетов нашлось. Если < 4 — тема падает вниз. Это спасает от
   ситуации «сценарий написан, а показывать нечего».
7) Output: topics_queue.json (топ-N), плюс выбранная тема → topic.json.

5.4. СКРИНШОТЫ СТАТЕЙ И ГАЗЕТ (то, что заказчик просил отдельно)
--------------------------------------------------------------------------------
Два пути, оба обязательны:

ПУТЬ 1 — «живой скриншот» (Playwright, headless Chromium):
  - viewport 1440x2000, deviceScaleFactor 2, prefers-color-scheme: dark
  - block: cookie-баннеры, попапы, рекламу (список селекторов + uBlock-правила)
  - ждать networkidle + 600 ms
  - снимать НЕ всю страницу, а элемент-кластер: h1 + подзаголовок + hero-image
    + первый абзац. Если элемент не найден — фолбэк на путь 2.
  - постобработка: скругление 20 px, тень, лёгкий наклон 2°, затемнение до
    яркости 0.82, добавление crimson-подчёркивания под ключевой фразой
    (координаты фразы получаем через page.evaluate + Range.getBoundingClientRect).

ПУТЬ 2 — «синтетическая карточка» (когда пейволл/капча/уродливая вёрстка):
  - извлекаем через readability: заголовок, дата, автор, лид, hero-image
  - рендерим СВОЮ карточку в брендстиле (HTML-шаблон
    render/templates/news_card.html): Deep Void фон, Space Grotesk заголовок,
    Inter лид, JetBrains Mono дата, логотип издания (favicon 128px),
    тонкая crimson-линия слева.
  - это выглядит премиальнее и всегда консистентно с брендом.

ПРАВИЛА ПОКАЗА (важно для авторских прав и YouTube):
  - скриншот статьи в кадре не дольше 3.0 c;
  - всегда видна атрибуция: домен издания + дата мелким кеглем (#94A3B8);
  - максимум 2 скриншота статей на ролик;
  - цитата из статьи в кадре — не более 12 слов, всегда в кавычках с источником;
  - фото из статьи НЕ переиспользуем как футаж (только внутри карточки-скриншота),
    для футажа берём лицензионно чистые NASA/ESA/сток/архив.

================================================================================
6. STAGE 01 — RESEARCH PACK
================================================================================

Задача: превратить тему в проверенный набор фактов с источниками, из которых
сценарист физически не сможет сочинить неправду.

6.1. АЛГОРИТМ
--------------------------------------------------------------------------------
1) Собрать 3–6 источников по кластеру темы (из topic.json + добор поиском).
2) Скачать полный текст (readability), обрезать до 12 000 символов на источник.
3) Grok (текст): извлечь атомарные утверждения.
   Каждое утверждение = {claim, value, unit, source_idx, confidence, quote≤12 слов}
4) Кросс-верификация: утверждение принимается, если
   - подтверждено ≥2 независимыми источниками, ИЛИ
   - есть у первоисточника с authority ≥0.85 (NASA/ESA/Nature/arXiv).
   Иначе → в блок "unverified", и в сценарий такие цифры НЕ ПОПАДАЮТ.
5) Числа проходят sanity-check (единицы, порядок величины, диапазон).
   Расхождение между источниками >10% → берём диапазон и в скрипте говорим
   «около» / «по разным оценкам».
6) Отдельно собираем visual_hooks: что конкретно можно показать
   (снимок JWST, схема орбиты, сравнение размеров, кадр запуска, график).
7) Сохраняем 1–2 скриншота статей (раздел 5.4).

6.2. research_pack.json
--------------------------------------------------------------------------------
{
  "topic_id":"...",
  "verified_claims":[
    {"id":"c1","claim":"...","value":124,"unit":"св.лет","sources":[0,2],
     "confidence":0.94,"quote":"...","visualizable":true}
  ],
  "unverified":[...],
  "visual_hooks":[
    {"id":"v1","what":"снимок JWST области NGC 604","where":"NASA library",
     "query_en":"JWST NGC 604 infrared","priority":1}
  ],
  "article_screenshots":[{"file":"screens/nature_2026.png","domain":"nature.com",
                          "date":"2026-08-08","headline":"..."}],
  "glossary":[{"term":"диметилсульфид","simple":"газ, который на Земле
               производят только живые организмы"}]
}

ПРАВИЛО АНТИГАЛЛЮЦИНАЦИИ: в script.json попадают только claim.id из
verified_claims. Валидатор s02 проверяет: каждая цифра/утверждение в сценарии
имеет ссылку на claim_id. Нет ссылки — стадия падает с ошибкой,
а не «примерно так».

================================================================================
7. STAGE 02 — SCRIPT WRITER
================================================================================

7.1. ФОРМА СЦЕНАРИЯ
--------------------------------------------------------------------------------
Хронометраж: 38–52 c (целевой 45 c). Слов: 105–140 (темп ~155 слов/мин — плотно,
как в референсах, но без скороговорки).
Структура (жёсткая):
  HOOK    0.0–2.0 c   1 предложение, ≤12 слов, содержит парадокс или масштаб.
  SETUP   2.0–8.0 c   что именно произошло и почему это вообще важно.
  BODY    8.0–30.0 c  2–3 факта, каждый с числом и с визуальной опорой.
  CLIMAX  30.0–40.0c  самое сильное следствие/смысл.
  CLOSER  40.0–45.0c  вопрос / пуант / петля + CTA.

7.2. TONE OF VOICE (из брендбука, дословно в промпт)
--------------------------------------------------------------------------------
  - Точный, но не сухой. Спокойный, уверенный, с внутренним огнём.
  - Лёгкая поэзия допустима («на краю горизонта событий…»), но не более одного
    поэтического образа на ролик.
  - Уважает интеллект зрителя: не объясняет очевидное, не сюсюкает.
  - Без панибратства, без академического занудства.
  - Лёгкая ирония — можно. Сарказм и кликбейт-ложь — НЕТ.
  - Главная эмоция: тихий восторг + ясность.

7.3. ЗАПРЕЩЁННЫЕ КОНСТРУКЦИИ (валидатор отклоняет автоматически)
--------------------------------------------------------------------------------
  «Учёные шокированы», «вы не поверите», «это изменит всё навсегда»,
  «топ-5 фактов, которые», «смотрите до конца», «подпишись, если не знал»,
  «представьте себе» в первом предложении, риторическое «а знаете ли вы».
  Также: любые утверждения о лечении/диагнозе в императиве; любые прогнозы,
  поданные как факт; слова «доказано», если в источнике «предполагается».

7.4. ОБЯЗАТЕЛЬНАЯ РАЗМЕТКА ВЫХОДА
--------------------------------------------------------------------------------
Сценарист сразу размечает биты, эмоции и визуальные намерения — это то, из чего
Shotlist Director потом строит монтаж. Без этой разметки следующая стадия не
работает.

script.json:
{
  "topic_id":"...",
  "closer_type":"CLOSER_LOOP",
  "total_words":127,
  "beats":[
    {"id":"b01","section":"HOOK","text":"Джеймс Уэбб поймал в атмосфере
      чужой планеты газ, который на Земле делают только живые организмы.",
     "claim_ids":["c1","c3"],
     "entities":["Джеймс Уэбб","K2-18b","диметилсульфид"],
     "emotion":"awe",            // awe|tension|irony|shock|calm|urgency|hope
     "visual_intent":"COSMIC_HERO", // см. словарь 8.3
     "emphasis_words":["только живые организмы"],
     "meme_slot":false,
     "must_show":"снимок экзопланеты/атмосферы",
     "duration_hint_s":2.0}
  ],
  "cta_text":"А вы бы полетели проверить?",
  "title_ru":"...","description_ru":"...","hashtags":["#космос","#JWST",...],
  "pinned_comment":"Источники: ..."
}

7.5. ВАЛИДАТОР СЦЕНАРИЯ (запускать до s03)
--------------------------------------------------------------------------------
  V1 каждое число в тексте имеет claim_id из research_pack → иначе fail
  V2 нет запрещённых конструкций (7.3)
  V3 длительность по формуле words/155*60 в диапазоне 38–52 c
  V4 HOOK ≤12 слов и содержит либо число, либо парадокс
  V5 у каждого бита заполнены emotion и visual_intent
  V6 meme_slot=true не более чем у 2 битов и только в BODY/CLIMAX/CLOSER
  V7 CLOSER присутствует и соответствует closer_type
  V8 нет медицинских рекомендаций, нет политических оценок

================================================================================
8. STAGE 03 — SHOTLIST DIRECTOR (РАСКАДРОВКА И РИТМ)
================================================================================

Это сердце «динамичного монтажа». Здесь текст превращается в план кадров с
точностью до кадра, ещё до того, как найден хоть один ассет.

8.1. ВХОД: script.json + words.json (пословные тайминги VO из s09, если уже
готовы; если нет — оценочные тайминги, потом пересчёт в s10).

8.2. АЛГОРИТМ
--------------------------------------------------------------------------------
1) Разбить каждый бит на SHOT'ы по правилу «одна сущность — один кадр»
   (главный вывод из V2): смотрим на entities и на существительные-объекты.
   Прозвучала сущность → под неё отдельный кадр.
2) Назначить длительности из профиля ритма (2.3) с учётом режима (2.1).
3) Назначить режим кадра по правилам R1–R9 (2.2) + эвристикам:
     visual_intent = COSMIC_HERO | SIMULATION | DATA_VIZ  → MODE_B
     visual_intent = UI_WALKTHROUGH | ARTICLE | DIAGRAM   → MODE_A
     visual_intent = DIRECT_ADDRESS | QUESTION | THESIS   → MODE_C
     emotion = irony|shock и meme_slot=true                → MODE_B (мем)
4) Расставить BURST'ы: если бит содержит перечисление (≥3 однородных сущности)
   или section=CLIMAX → BURST из N=len(items) кадров по 0.18–0.30 c.
5) Расставить переходы и звуковые события (каждая смена режима — звук).
6) Сгенерировать для каждого шота ПОИСКОВОЕ НАМЕРЕНИЕ: три уровня запросов
   (раздел 9.2) — их потом использует Asset Hunter.
7) Проверить сумму длительностей == длительность VO (±0.15 c). Если не сходится —
   растянуть/сжать шоты пропорционально в пределах допусков режима.

8.3. СЛОВАРЬ visual_intent → ЧТО ИСКАТЬ
--------------------------------------------------------------------------------
  COSMIC_HERO     реальные снимки телескопов, NASA/ESA, туманности, планеты
  SIMULATION      рендеры, симуляции, слоу-мо процессов, CGI-визуализации
  DATA_VIZ        график/бар/сравнение → генерируем сами (раздел 13)
  DIAGRAM         схема связи объектов → генерируем сами (PROCESS_ARROW)
  ARTICLE         скриншот статьи/поста (раздел 5.4)
  UI_WALKTHROUGH  запись экрана интерфейса, скриншот продукта
  ICON_LOGO       логотип компании/модели → сток-иконка + брендовая карточка
  LAB_TECH        лаборатории, чипы, роботы, дата-центры, микроскопия
  HUMAN_SCALE     человек рядом с объектом — для передачи масштаба
  ABSTRACT_NEURAL нейронные поля, частицы, потоки данных (брендовые backplates)
  ARCHIVE         исторические кадры (Internet Archive), запуски, хроника
  MEME            вставка из мем-базы (раздел 12)
  PRESENTER_ONLY  только лицо, без оверлеев (для сильной фразы)

================================================================================
9. STAGE 04 — ASSET HUNTER (УМНЫЙ ПОИСК МАТЕРИАЛА)
================================================================================

9.1. ПРИНЦИП: «дёшево → дорого, локально → в сеть, точно → приблизительно».
Никогда не начинаем с платной генерации. Генерация — последний шаг.

9.2. ТРИ УРОВНЯ ЗАПРОСОВ (генерирует s03, использует s04)
--------------------------------------------------------------------------------
  L-literal     точные сущности как есть: "K2-18b exoplanet", "Hugging Face logo"
                → идёт в NASA/архивы/новостные медиа/иконки
  L-conceptual  визуальная метафора смысла: "alien atmosphere spectral analysis",
                "data breach red alert server room"
                → идёт в сток и в генерацию
  L-stock_en    generic-английский, как реально тегируют сток:
                "nebula 4k", "server room dark", "scientist looking at screen"
                → Pexels/Pixabay/Magnific-stock

ПРАВИЛО: literal-запросы НИКОГДА не отправляем в генеративные модели с именами
реальных людей. Для персон используем только новостные фото/архив с атрибуцией.

9.3. ЛЕСТНИЦА ИСТОЧНИКОВ (порядок обхода, останов при достаточности)
--------------------------------------------------------------------------------
  1. LOCAL CACHE (cache/objects + assets/backplates)            стоимость 0
  2. NASA Image & Video Library (images-api.nasa.gov)           0, public domain
  3. ESA / Webb / archive.org (CC/PD коллекции)                 0
  4. Pexels / Pixabay                                           0
  5. Magnific — поиск по стоку (Freepik: фото, видео, иконки)   дёшево
  6. Magnific — генерация изображения (бесплатные модели)       кредиты
  7. Magnific — генерация видео (бесплатные модели)             кредиты, лимит 2
  8. Grok — генерация изображения                               токены, резерв
  9. Процедурный брендовый backplate                            0 (последний шанс)

ПРАВИЛО ДОСТАТОЧНОСТИ: для шота собираем кандидатов, пока не наберём
  - 3 кандидата для priority=1 шота,
  - 2 кандидата для priority=2,
  - 1 кандидат для priority=3.
Как только набрали — переходим к следующему шоту. Не «собираем всё подряд» —
это главный пожиратель кредитов.

9.4. ИКОНКИ И ЛОГОТИПЫ (кейс заказчика: «скачал иконку ChatGPT, нарисовал
     стрелочку в сторону Hugging Face»)
--------------------------------------------------------------------------------
  - Логотипы берём: Magnific/Freepik icon search → simpleicons (SVG, CDN) →
    официальный press-kit домена → favicon 256px как последний фолбэк.
  - Приводим к брендовому виду: помещаем в «капсулу» — круг 320 px,
    фон rgba(241,245,249,.06), обводка rgba(241,245,249,.14), внутри лого,
    под ним подпись Inter Medium 28 px.
  - Хранить в cache/objects + icons_index.json (чтобы не качать повторно).
  - Все логотипы используются только в информационном контексте (номинативное
    использование), без намёка на партнёрство/одобрение.

9.5. ТЕХНИЧЕСКАЯ НОРМАЛИЗАЦИЯ КАЖДОГО СКАЧАННОГО АССЕТА (ffmpeg, локально)
--------------------------------------------------------------------------------
  - ffprobe → width, height, duration, fps, has_audio
  - motion_score = средняя абсолютная разница кадров (0..1); статичное фото = 0
  - sharpness = дисперсия Лапласиана по центральному кропу
  - phash (64 бит) для дедупа
  - dominant_colors (5 кластеров) → проверка на «кислотность» (см. 10.2)
  - has_faces (быстрый детектор) → для правил приватности и композиции
  - has_text (быстрый OCR на 3 кадрах) → если крупный текст на чужом языке
    в центральной зоне — минус в оценке
  - watermark_suspect = детект повторяющегося полупрозрачного паттерна в углах
    (сравнение краевых зон трёх кадров + сопоставление с базой типовых вотермарок)
  Всё это пишется в <sha256>.meta.json и используется L0-фильтром БЕСПЛАТНО.

9.6. АНТИПОВТОР
--------------------------------------------------------------------------------
  - Ассет, использованный в последних 30 роликах, получает −4 к итоговой оценке
    (но не запрещён: бывают «фирменные» кадры).
  - Ассет, использованный в этом же ролике, запрещён полностью.
  - pHash-дистанция ≤10 к уже выбранному в этом ролике → отклонить (визуальный
    самоповтор в пределах одного видео убивает ощущение динамики).

    "author":"NASA/ESA/CSA","w":3840,"h":2160,"duration":0,
    "motion":0.0,"sharpness":312.4,"phash":"...","faces":0,"text":false,
    "watermark_suspect":false,"query_used":"literal:0",

}

================================================================================
10. STAGE 05 — CRITIC (ДВУХСЛОЙНЫЙ КРИТИК)
================================================================================

Критик — отдельный, самостоятельный модуль. Может работать автономно
(`make critic RUN=<id>`), может — в связке с vision-моделями Grok и Gemini.
Его задача: отсеять неподходящее, объяснить ПОЧЕМУ и выдать улучшенный запрос
для добора.

10.1. L0 — ДЕТЕРМИНИРОВАННЫЙ ФИЛЬТР (без ИИ, стоимость 0). Отсекает 50–70%.
--------------------------------------------------------------------------------
Жёсткие отказы (hard reject):
  - короткая сторона < 1080 px (для видео) / < 1440 px (для фото под ken burns)
  - duration < длительности шота (для видео) и нет возможности зациклить
  - watermark_suspect = true
  - sharpness ниже порога (размыто/апскейл-мыло)
  - лицензия не разрешает коммерческое использование
  - phash-дубль уже выбранного в этом ролике
  - крупный читаемый текст чужого бренда в центре кадра
Мягкие штрафы (влияют на l0_score 0–10):
  - motion_score < 0.02 в MODE_B (статика в динамичном режиме) → −2
    (лечится ken burns, поэтому не hard reject)
  - «кислотные» цвета: если доля пикселей с saturation>0.85 и hue вне
    диапазонов crimson/blue/void > 18% → −3 (брендбук запрещает кислоту)
  - соотношение сторон далеко от 9:16 и объект интереса у края → −2
  - наличие лиц крупным планом в шоте, где это не нужно → −1
  - повтор из истории 30 роликов → −4

10.2. L1 — VLM-КРИТИК (Grok vision основной, Gemini — арбитр)
--------------------------------------------------------------------------------
ГЛАВНЫЙ ПРИЁМ ЭКОНОМИИ (обязателен к реализации):
  Не отправлять картинки по одной. Собирать КОНТАКТНЫЙ ЛИСТ:
  сетка 3x3 из 9 кандидатов, каждая плитка 360x640, с крупным номером 1–9
  в левом верхнем углу плитки (рисуем через ffmpeg drawtext).
  Один vision-вызов оценивает сразу 9 кандидатов и возвращает JSON-массив.
  Экономия — примерно в 7–9 раз по сравнению с поштучной оценкой.
  Для видео-кандидатов берём 1 репрезентативный кадр (на 40% длительности).

Критерии оценки (0–10 каждый), веса в config/critic.yaml:
  relevance        0.30  соответствует ли кадр смыслу фразы, а не только теме
  factual_fit      0.25  не показывает ли неверный объект/эпоху/технологию
                         (пример ошибки: говорим про JWST — показываем Hubble)
  brand_fit        0.20  тёмная палитра, премиальность, отсутствие «дешёвого
                         midjourney-look», нет кислоты и грязного киберпанка
  wow              0.15  останавливает ли взгляд
  safety           0.10  нет крови/жести/узнаваемых частных лиц/чужих вотермарок
Итог: weighted score. Порог принятия по умолчанию 7.0.
       priority=1 шоты — порог 7.5. Фолбэк-шоты — 6.0.

Ответ модели строго JSON:
[{"i":1,"relevance":8,"factual_fit":9,"brand_fit":7,"wow":6,"safety":10,
  "verdict":"keep","reason":"телескоп с золотым зеркалом, точное попадание",
  "better_query":null},
 {"i":2,"...":"...","verdict":"reject","reason":"это Hubble, не JWST",
  "better_query":"James Webb Space Telescope golden hexagonal mirror"}]

10.3. АРБИТРАЖ GEMINI (только когда это оправдано — экономия)
--------------------------------------------------------------------------------
Gemini vision вызывается ТОЛЬКО если выполняется одно из:
  - оценка Grok попала в «серую зону» 6.5–7.5 у priority=1 шота;
  - factual_fit ≤ 7 при наличии в шоте именованной сущности (риск показать
    не тот объект — самая дорогая ошибка для научпопа);
  - кандидат идёт на обложку/хук (первые 2 секунды).
Максимум 3 вызова Gemini на ролик (budget.yaml).
Правило консенсуса:
  |grok − gemini| ≤ 2  → берём среднее
  |grok − gemini| > 2  → кандидат отклоняется автоматически (спорный ≠ хороший)

10.4. КРИТИК СЦЕНЫ, А НЕ ТОЛЬКО КАРТИНКИ (второй проход, дешёвый)

Grok оценить:
  - визуальное разнообразие (нет ли трёх похожих кадров подряд),

  - работает ли хук как хук.
Возврат: список shot_id, которые стоит заменить, с причиной.
Это ровно один дополнительный vision-вызов, а качество монтажа поднимает сильно.

12. STAGE 07 — MEME DIRECTOR (ЛОГИКА МЕМОВ)
================================================================================

ФИЛОСОФИЯ (следовать буквально): мем — это ЗНАК ПРЕПИНАНИЯ, а не контент.
Он ставится там, где зритель и так уже почувствовал эмоцию, и мем её называет.
Мем не объясняет факт. Мем реагирует на факт.
Лучше НОЛЬ мемов, чем один натянутый. Натянутый мем ломает позиционирование
«премиальный проводник» сильнее, чем скучный кадр.

12.1. ИНДЕКС МЕМ-БАЗЫ (assets/memes/memes.index.json)
--------------------------------------------------------------------------------
Разметить один раз (можно полуавтоматически: Grok vision по контактному листу
из 9 мемов за вызов → 3–4 вызова на всю базу из 30 штук).

{
 "id":"m07","file":"files/devito_confused.mp4","duration":0.85,"has_audio":true,
 "emotion":["skepticism","confusion"],      // главный ключ подбора
 "intensity":2,                              // 1 тонко … 3 громко
 "register":"dry",                           // dry|absurd|slapstick|deadpan
 "reads_in_ms":350,                          // за сколько считывается смысл
 "safe_topics":["ai","it","tech","science_general"],
 "banned_topics":["medicine","death","disaster","war","children","religion"],
 "requires_context":false,
 "last_used":"2026-07-28","use_count":3
}

12.2. КОГДА МЕМ РАЗРЕШЁН (все условия должны выполниться)
--------------------------------------------------------------------------------
  C1 Тема ролика в pillar ∈ {ai, it_news, tech} или science с ироничным углом.
  C2 Бит помечен сценаристом meme_slot=true И emotion ∈
     {irony, shock, skepticism, smugness, disappointment, panic}.
  C3 Позиция бита: BODY (после контринтуитивного факта), CLIMAX,
     или CLOSER (пуант). В HOOK и SETUP мемы ЗАПРЕЩЕНЫ — там строим доверие.
  C4 Тема не входит в banned_topics мема.
  C5 Этот мем не использовался последние 15 роликов.
  C6 В ролике ещё не стоит 2 мема (жёсткий потолок).
  C7 Глобальная частота: не более чем в 40% роликов вообще есть мем.
     Счётчик ведётся в memes_usage.json; если за последние 10 роликов мемы
     были в 4+ — новый мем не ставится (кроме прямого указания оператора).

12.3. ГЛОБАЛЬНЫЕ ЗАПРЕТЫ (hard, без исключений)
--------------------------------------------------------------------------------
  - Смерть, болезни, пациенты, катастрофы, аварии с жертвами, война.
  - Любая медицинская тема с реальными людьми.
  - Этические споры про ИИ, где есть пострадавшие стороны.
  - Космические трагедии (Челленджер, Союз-11 и т.п.).
  - Религия, национальность, политические фигуры в оценочном контексте.
  - Мем поверх скриншота реальной статьи (выглядит как насмешка над изданием).

12.4. АЛГОРИТМ ВЫБОРА (дешёвый: максимум 1 LLM-вызов на ролик)
--------------------------------------------------------------------------------
1) Отобрать биты-кандидаты по C1–C3.
2) Отфильтровать базу по emotion бита + banned_topics + cooldown (C4–C5).
   Если после фильтра пусто → мема нет, идём дальше. Это нормально.
3) Взять топ-5 кандидатов (по совпадению emotion и по давности использования).
4) ОДИН вызов Grok: дать текст бита ± соседние фразы и список из 5 мемов
   (описание + emotion + register), попросить:
     - выбрать лучший или ответить "none";
     - дать fit_score 0–10 и обоснование в одном предложении;
     - предложить точку вставки: "before_phrase" | "on_phrase" | "after_phrase".
5) ПОРОГ: fit_score ≥ 8 → ставим. 7 → ставим только в CLOSER. <7 → не ставим.
   Порог намеренно высокий: мемов должно быть мало и они должны быть точными.
6) Опционально (если бюджет позволяет и мем визуально неоднозначен): проверить
   выбор через Gemini vision по одному кадру мема — «читается ли эмоция за
   0.5 секунды без контекста». <7 → отменяем.

12.5. ФОРМА ВСТАВКИ (монтажная механика — то, что делает «круто»)
--------------------------------------------------------------------------------
  - Длительность в кадре: 0.45–0.90 c. Дольше — теряется темп.
  - Вход: FLASH 2 кадра (crimson 45%) + жёсткая склейка + sfx impact_soft.
  - Режим: MODE_B на весь кадр (или PiP 34% в правом нижнем углу, если ведущий
    в этот момент договаривает важную фразу).
  - Звук мема: если has_audio — поднять до −8 dB, VO приглушить на −6 dB,
    музыку на −4 dB. Если мем без звука — обязательно подложить sfx.
  - Субтитры на время мема СКРЫВАЮТСЯ (кроме одного слова-реакции, если оно
    усиливает шутку).
  - Выход: жёсткая склейка обратно, без плавных переходов. Плавный выход из
    мема убивает панч.
  - После мема следующий шот обязан быть «серьёзным» и длиться ≥1.4 c —
    это возврат к спокойной интонации бренда.

14.1. ПОРЯДОК (важно для экономии кредитов)
--------------------------------------------------------------------------------

5) Полученный avatar.mp4 нормализовать: 1080x1920, 30 fps, привести
   аудио-дорожку к vo.wav (использовать VO как мастер, дорожку аватара
   выбросить — так липсинк остаётся, а звук один и тот же).
6) Кадрирование аватара под режимы делается ЛОКАЛЬНО из одного файла:
   MODE_C — полный кадр; MODE_A — кроп нижней половины с масштабом 1.18;

16. STAGE 11 — RENDER (HYPERFRAMES + GITHUB ACTIONS)

16.1. АДАПТЕР
--------------------------------------------------------------------------------
src/render/hyperframes_adapter.py переводит timeline.json в задание HyperFrames.
Требования:
  - Адаптер — единственное место, знающее про формат HyperFrames. Если API
    поменяется, правится один файл.
  - Обязательная валидация timeline против схемы (pydantic) ДО отправки.
  - Все пути к медиа — абсолютные, файлы предварительно скопированы в
    runs/<run_id>/media/ (HyperFrames не должен ходить в кэш напрямую).
  - Идемпотентность: job_id сохраняется в state.json; повторный запуск сначала
    проверяет статус существующего job, а не создаёт новый.

16.2. ВЫХОДНОЙ ФАЙЛ
--------------------------------------------------------------------------------
  1080x1920, H.264 High, 30 fps (или 60 fps для роликов с ≥1 BURST — из замера
  V2, который снят в 60 fps и потому выглядит плавнее на быстрых кадрах),
  CRF 18 / bitrate 14–16 Mbps, yuv420p, faststart,
  аудио AAC 320 kbps, −14 LUFS integrated, true peak ≤ −1.5 dBTP.

16.3. GITHUB ACTIONS — produce.yml (структура)
--------------------------------------------------------------------------------
name: produce
on:
  workflow_dispatch:
    inputs: {topic_id: {required: false}, dry_run: {default: "false"}}
  schedule: [{cron: "0 6 * * *"}]
concurrency: {group: redshift-produce, cancel-in-progress: false}
jobs:
  produce:
    runs-on: ubuntu-latest
    timeout-minutes: 60
    steps:
      - checkout
      - setup-python 3.11 + cache pip
      - apt-get install ffmpeg fonts + playwright install chromium
      - restore cache:
          key: redshift-assets-${{ hashFiles('config/sources.yaml') }}
          path: cache/
      - run: make produce TOPIC=${{ inputs.topic_id }} DRY=${{ inputs.dry_run }}
      - upload-artifact: runs/${{ env.RUN_ID }}  (state, json'ы, логи)  if: always()
      - upload-artifact: out/*.mp4                                      if: success()
      - save cache: cache/                                              if: always()
      - run: make notify-telegram                                       if: always()

ВАЖНО: шаг save cache обязан идти с if: always() — иначе при падении вся
скачанная за прогон медиатека теряется, и добор материала начнётся с нуля.
Это прямое требование заказчика «если ролик падает — сохраняй всё в кэш».

16.4. resume.yml
--------------------------------------------------------------------------------
Вход: run_id. Шаги: восстановить cache → скачать артефакт прошлого прогона →
`make resume RUN=<run_id>` → продолжить со стадии, где status != done.
Стадии со status=done пропускаются по hash-проверке, бюджет не тратится.

Прямое требование заказчика: «следи за токенами, чтоб их не жечь попусту».

E1. КОНТАКТНЫЙ ЛИСТ ВМЕСТО ПОШТУЧНОЙ ОЦЕНКИ
    9 кандидатов = 1 vision-вызов вместо 9. Плитки 360x640, JPEG q72,

E2. L0 ПЕРЕД L1 ВСЕГДА
    Детерминированные фильтры отсекают 50–70% мусора бесплатно. В vision

E3. ДАУНСКЕЙЛ ДЛЯ VISION

E4. КЭШ LLM ПО ХЭШУ ПРОМПТА
    cache/llm/. Одинаковый промпт при одинаковой модели и параметрах не
    вызывается дважды никогда, в том числе между разными роликами.

E5. СТАБИЛЬНЫЙ СИСТЕМНЫЙ ПРОМПТ
    Все промпты строятся как [неизменяемый system] + [переменная часть].
    Неизменяемая часть одинакова между вызовами — это позволяет провайдеру
    кэшировать префикс и снижает цену. Не перемешивать порядок блоков.

E6. КОРОТКИЕ СХЕМЫ ОТВЕТА
    Просить JSON с однобуквенными/короткими ключами там, где ответ длинный
    (критик: i, r, f, b, w, s, v). Разворачивать в полные имена локально.
    На 27 кандидатах это ощутимая экономия выходных токенов.

E7. ЛИМИТ КОНТЕКСТА НА ВХОДЕ
    В research не отправлять полные статьи: readability → обрезка до
    12 000 символов → и только 3–6 источников. Не «всё, что нашли».

E8. ОДИН РЕНДЕР АВАТАРА
    HeyGen вызывается ровно один раз на ролик. Все режимы кадра получаются

E9. ГЕНЕРАЦИЯ — ПОСЛЕДНЯЯ СТУПЕНЬ

================================================================================
20. ВОССТАНОВЛЕНИЕ ПОСЛЕ ПАДЕНИЯ (RESUME ИЗ КЭША)
================================================================================

Требование заказчика дословно: «Если ролик падает — сохраняй всё в кэш и
переделывай с добором материала и использованием из кэша».

20.1. ЧТО СОХРАНЯЕТСЯ НЕМЕДЛЕННО (не в конце, а по мере получения)
--------------------------------------------------------------------------------
  - каждый скачанный файл → cache/objects/<sha256> + .meta.json СРАЗУ
  - каждый ответ LLM → cache/llm/ СРАЗУ после получения
  - каждый артефакт стадии → runs/<id>/ атомарной записью
  - state.json обновляется после каждой стадии и после каждых 10 скачиваний
  - при исключении — обработчик пишет state.stages[X].status="failed" с
    traceback и partial-артефактом, и только потом падает

20.2. КОМАНДА ВОССТАНОВЛЕНИЯ
--------------------------------------------------------------------------------
  make resume RUN=2026-08-10_jwst_01 [FORCE_REFILL=true] [FROM=s05]
Логика:
  1) Прочитать state.json.
  2) Проверить целостность артефактов done-стадий (файл существует, JSON
     валиден, hash совпадает). Битые → пометить pending.
  3) Стартовать с первой не-done стадии (или с FROM).
  4) Все сетевые вызовы сначала бьют в кэш → повторное скачивание не
     происходит, бюджет не тратится.
  5) Если FORCE_REFILL=true — принудительно запустить GAPFILL для шотов
     с оценкой критика <8.0, даже если они формально «done».
  6) Если причина падения — нехватка материала (например, критик отклонил
     всё по шоту), resume автоматически спускается на ступень ниже по
     лестнице источников и разрешает генерацию.

20.3. ЗАЩИТА ОТ БЕСКОНЕЧНОГО ЦИКЛА
--------------------------------------------------------------------------------
  - attempts на стадию ≤3. После третьего падения — стадия помечается
    degraded, применяется фолбэк, ролик идёт дальше.
  - Общий wallclock на прогон 35 минут (budget.yaml). По превышении —
    принудительная деградация до LVL 5 и сборка того, что есть.

20.4. GARBAGE COLLECTION КЭША
--------------------------------------------------------------------------------
  - cache/objects чистится только по явной команде `make gc DAYS=180`
    и никогда автоматически (иначе теряется главная экономия).
  - cache/queries и cache/llm чистятся по TTL при каждом запуске.
  - Ассеты, помеченные used_in_published=true, из GC исключаются навсегда
    (нужны для повторных рендеров и для проверки антиповтора).

23.1. СОДЕРЖИМОЕ ФАЙЛА .cursorrules (положить в корень репозитория)
--------------------------------------------------------------------------------
# REDSHIFT Shorts Factory — правила для агента

## Роль
Ты — инженер конвейера генерации коротких видео. Источник правды —
docs/REDSHIFT_SHORTS_FACTORY_TZ.txt. При конфликте кода и ТЗ прав ТЗ.

## Архитектурные инварианты (нарушать нельзя)
1. Каждая стадия pipeline читает ровно один входной JSON и пишет ровно один
   выходной JSON в runs/<run_id>/. Никаких скрытых зависимостей.
2. Все внешние вызовы идут через src/clients/*, обёрнутые в
   cache → budget → retry → cost-log. Прямой HTTP в pipeline запрещён.
3. Все числовые константы — в config/*.yaml. Магические числа в коде = ошибка.
4. Все артефакты валидируются pydantic-моделями из src/core/schemas.py.
5. Любая стадия должна работать с --dry-run на фикстурах, без сети и токенов.
6. Никогда не логируй секреты. Ключи только из os.environ / GH secrets.
7. Идемпотентность: повторный запуск стадии с тем же входным хэшем не тратит
   бюджет и не перезаписывает валидный артефакт.

## Стиль
- Python 3.11, type hints обязательны, ruff + black.
- Функции ≤60 строк. Один модуль — одна ответственность.
- Ошибки — свои классы в core/errors.py, никаких голых except.
- Логи структурные (json), одна строка = одно событие, всегда с run_id и stage.

## Тесты
- На каждую стадию: тест на фикстурах + тест на валидацию схемы.
- На критика: тест, что L0 отсекает заведомо плохие метаданные.
- На ритм: тест, что сгенерированный shotlist проходит проверки раздела 8.4.
- На бюджет: тест, что превышение лимита вызывает деградацию, а не падение.

## Чего не делать
- Не переписывать существующий рабочий рендер-адаптер без необходимости.
- Не добавлять новые внешние зависимости без явной причины в PR-описании.
- Не «улучшать» тайминги и палитру по своему вкусу — они из брендбука.
- Не заменять детерминированные проверки на вызовы LLM (дорого и нестабильно).

  [ ] Не содержит магических чисел.

25.2. ЧЕК-ЛИСТ ГОТОВОГО РОЛИКА (то, что смотрит человек перед публикацией)
  [ ] В первые 0.4 c есть визуальный хук и крупный текст.
  [ ] Ни один план не «провисает» — субъективно ролик не даёт заскучать.
  [ ] Лицо ведущего освещено, crimson fill с той же стороны, что всегда.
  [ ] Текст ни разу не перекрыл глаза и рот.
  [ ] Все цифры на экране совпадают с озвучкой.
  [ ] Скриншот статьи — с атрибуцией и не дольше 3 c.
  [ ] Мем (если есть) вызывает улыбку, а не недоумение.
  [ ] Финал: вопрос/пуант/петля + SUBSCRIBE в последние 2 c.
  [ ] Ролик выглядит как REDSHIFT за первые 0.8 секунды.

25.3. МЕТРИКИ, КОТОРЫЕ СИСТЕМА ДОЛЖНА СЧИТАТЬ САМА (для эволюции канала)
  - медиана интервала склеек по каждому опубликованному ролику;
  - доля ведущего в кадре;
  - количество мемов и их fit_score;
  - средняя оценка критика по принятым кадрам;
  - стоимость ролика (токены/кредиты) и её тренд;
  - degradation_level;
  - удержание с YouTube Analytics по секундам, сопоставленное с монтажной
    сеткой (какие типы кадров теряют зрителя) — сохранять в analytics.jsonl.
  Через 20–30 роликов эти данные позволят подтянуть config/rhythm.yaml

27. ПРИЛОЖЕНИЕ B — ЮРИДИЧЕСКИЕ И ПЛАТФОРМЕННЫЕ ОГРАНИЧЕНИЯ
================================================================================

B1. ЛИЦЕНЗИИ МАТЕРИАЛА
  - NASA/ESA/Webb — общественное достояние, но требуется корректная атрибуция
    (NASA/ESA/CSA + инструмент). Атрибуцию писать в описании ролика.
  - Pexels/Pixabay — свободно для коммерческого использования, атрибуция не
    обязательна, но храним источник в meta.json на случай спора.
  - Internet Archive — проверять поле rights каждой записи. Если рав не указан
    явно как PD/CC — НЕ использовать. Это частая ошибка, ведущая к страйкам.
  - Magnific/Freepik — соблюдать условия лицензии подписки, хранить id ассета.
  - Скриншоты статей — цитирование в информационных целях: небольшой фрагмент,
    видимая атрибуция, ссылка в описании, ≤3 c в кадре, ≤2 на ролик.
  - Мемы — использовать только собственную базу заказчика; кадры из фильмов и
    шоу держать в пределах коротких трансформативных вставок (<1 c) и не
    строить на них весь ролик.

B2. YOUTUBE
  - Shorts: вертикально, ≤60 c (целимся в 45 c).
  - Reused content: ролик обязан быть трансформативным — свой сценарий,
    свой голос, своя графика, своё лицо. Это выполняется по построению.
  - Медицинские темы: только описательно (что открыли учёные), без советов,
    дозировок и обещаний результата. Никаких «это лечит».
  - Фотосенситивность: не более 2 вспышек в секунду (см. rhythm.yaml).
  - Реальные люди: не ставить их в контекст, создающий ложное впечатление
    (нельзя монтировать так, будто человек сказал то, чего не говорил).
  - Не использовать в генеративных промптах имена и внешность реальных людей.

B3. ЧЕГО КАНАЛ НЕ ДЕЛАЕТ (позиционирование)
  - Не берёт политику, войны, катастрофы с жертвами.
  - Не делает кликбейт-заголовки с ложным обещанием.
  - Не выдаёт гипотезы за факты.
  - Не использует чужие ролики целиком как «свой» контент.
